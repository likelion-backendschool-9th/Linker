## 1. 목표와 적용 원칙

Linker에서 데이터를 처음 불러오거나 작업 결과를 기다릴 때 **Thinking Orb와 기존 한국어 상태 문구**를 함께 표시한다. A~E가 이후 만드는 화면도 같은 공통 컴포넌트·검사 기준을 사용한다. 데이터 요청·인증·결제·채팅 동작과 합의된 디자인을 유지하는 것이 도입의 전제다.

- 적용할 애니메이션은 사용자가 선택한 **Composing**이며 공통 어댑터에서 `state="composing"`으로 고정한다. Thinking Orb는 라이브러리/컴포넌트 이름이다. 화면별로 다른 모드를 고르지 않고 원본 Composing과 구현 결과의 크기·속도·색상을 비교한다.
- 20px는 기존 상태 문구 옆/버튼용, 64px는 이미 공간이 확보된 독립 대기 영역용이다. **모든 초기 로딩에 64px 영역을 새로 추가하지 않는다.** 기존 높이를 보존할 수 없는 화면은 20px 또는 기존 자리 안의 배치를 사용한다. 크기는 라이브러리 프리셋과 토큰을 일치시킨다.
- 피드·목록·상세의 스켈레톤은 콘텐츠 자리를 유지한다. Orb가 있는 영역에서는 스켈레톤의 pulse를 정적으로 바꿔 동시에 여러 애니메이션이 움직이지 않게 한다.
- 이미 표시된 콘텐츠를 배경 재조회 때문에 가리거나 전체 화면 로더로 되돌리지 않는다. 전체 화면을 덮는 전역 로딩 모달도 만들지 않는다.
- 실제 요청이 끝나면 즉시 성공/오류 화면으로 전환한다. 애니메이션을 보여주려고 응답을 늦추거나 가짜 진행률·완료 시점을 만들지 않는다.

앞선 `docs/thinking-orb-loading-plan`에서는 계획서만 작성했다. 현재는 사용자의 명시적 구현 요청에 따라 최신 dev에서 만든 `feat/thinking-orb-loading`에서 아래 작업을 진행한다. API·권한·DB·기존 레이아웃의 기능 변경은 포함하지 않는다.

### 1.1 최신 dev 대조 — 구현 전 확인

- `8ee7082` 이후 `13e23f0`의 공용 원격 DB 개발 설정(#136)이 추가됐다. 변경은 9개 파일이며 프론트 소스·패키지/lock·디자인 토큰·계획 기준 문서는 동일하다.
- 겹치는 예정 파일은 `.github/workflows/ci.yml`과 README다. 최신 CI의 원격 DB helper 경로 필터·단위 검사와 README의 DB 접속 링크를 보존한 상태에서 로딩 검사를 추가한다.
- 신규 DB 가이드·스크립트·설정·환경변수 예시는 로딩 구현 대상에서 제외한다. 테스트는 목업을 사용하고 실제 공용 DB에 연결하지 않는다.
- 기존 계획서는 미추적 파일 그대로 보존해 최신 dev에서 구현 브랜치를 만들었다. 기존 코드의 병합 충돌은 없으며, 구현 종료 직전 원격 dev의 추가 변경도 다시 확인한다.
- 공통 기반→라우트→화면 내부→검증/문서 순으로 변경을 구분한다. 동일 기능의 최종 통합 검증은 현재 구현 브랜치에서 수행하고, 검토 가능한 커밋/변경 묶음으로 나눈다. 최초 계획의 여러 PR 분리는 현재 구현 범위와 함께 재평가하며 dev에 자동 병합하지 않는다.

문서 검토만으로 Git 충돌이나 시각적 회귀가 없다고 보장하지 않는다. 아래의 공통 계약·변경 경계·비교 검증을 도입 완료 조건으로 삼는다. 충돌이 생기거나 기존 디자인/기능이 달라진 경우 해당 묶음은 통합하지 않고 수정 후 재검증한다.

이 계획서가 기존 PRD의 성능 규칙을 폐기하는 것은 아니다. 사용자의 구현 요청에 따라 제한된 Canvas 예외를 PRD·청사진·디자인 가이드와 코드에 함께 반영했다. 팀 검토는 구현 PR에서 수행한다. 다른 디자인 규칙을 완화하는 근거로 확대하지 않는다.

### 3.1 pnpm 설치·동기화 계약

저장소의 `frontend/package.json`은 `packageManager: pnpm@10.15.0`이며 웹 패키지 이름은 `web`이다. Node 최소 22/CI 24, 기존 workspace와 빌드 허용 목록은 유지한다. 아래 명령으로 웹 앱에만 정확한 버전을 설치했으며 frozen 설치도 확인했다.

```bash
# 저장소 루트에서 시작: 최초 추가는 구현자 한 명이 수행
cd frontend
pnpm --version
pnpm --filter web add --save-exact thinking-orbs@0.3.2
```

- 의존성은 `frontend/apps/web/package.json`의 dependencies에 정확한 버전으로 추가하고, `frontend/pnpm-lock.yaml`을 같은 PR에 포함한다.
- 프로젝트 의존성 설치에 npm/yarn을 섞거나 `package-lock.json`, `yarn.lock`, 앱별 별도 pnpm lockfile을 만들지 않는다. workspace 루트에 `-w add`로 넣거나 Expo 앱에 중복 설치하지 않는다.
- README/Dockerfile의 pnpm 도구 최초 설치 과정과 프로젝트 의존성 추가는 구분한다. 기존 도구 설치 방식을 바꾸는 작업은 포함하지 않는다.
- 설치 때문에 pnpm/React/Next/Motion 전체 버전을 올리거나 `pnpm-workspace.yaml`의 `onlyBuiltDependencies`를 넓히지 않는다. unrelated lock 변경은 원인을 확인하고 정리한다.

팀원은 공통 변경을 자신의 작업 브랜치에 반영한 후 다음만 수행한다. 각자 `add`를 다시 실행하거나 라이브러리를 별도로 복사할 필요는 없다.

```bash
# 저장소 루트에서 시작
cd frontend
pnpm --version
pnpm install --frozen-lockfile
pnpm dev:mock
```

pnpm 버전은 10.15.0으로 맞춘다. frozen 설치 실패 시 manifest/lock 또는 통합 상태를 확인하며, lockfile을 지우거나 CI의 frozen 옵션을 해제해 통과시키지 않는다. Docker 개발자는 호스트 manifest/lock을 함께 반영하고 개발 Watch의 의존성 재빌드를 확인한다. 운영 배포는 기존 main 이미지 빌드 절차를 따른다.

외부 컴포넌트를 화면마다 직접 import하지 않는다. 공통 공개 props는 `variant: 'block' | 'inline'`, 필수 `label`, 필요 시 기존 Skeleton을 받는 `children`, `announce`와 배경에 맞는 제한된 `tone`으로 구성한다. 모드·속도·숫자 크기·색상 문자열은 페이지에서 받지 않고 어댑터에 모은다. API 호출·요청 상태 저장은 로더에 넣지 않는다. `packages/ui`, 별도 Provider/Zustand 로딩 store는 신설하지 않는다.

컴포넌트와 검사 파일명은 위 경로로 확정했다. `labelHidden`은 기존에 상태 행이 없던 자리의 크기를 유지한다. Button은 `pendingLabel`로 버튼 바깥의 숨긴 상태 알림을 제공하며, 원래 액션 이름의 자리를 유지한 채 Orb를 겹친다. 청사진·lint·호출부도 같은 계약을 사용한다.

### 4.2 Server/Client 경계와 폴백

- `page.tsx`, `layout.tsx`, `loading.tsx`는 Server Component를 유지하고 Canvas 잎 컴포넌트만 Client Component로 둔다.
- SSR에서도 한국어 문구와 20/64px의 자리를 렌더링한다. Canvas가 준비될 때 레이아웃이 튀지 않게 한다.
- `window`, `document`, `matchMedia`, Canvas 접근은 effect/브라우저 가드 안에서만 수행한다. 첫 스파이크에서 Next 빌드와 hydration을 검증한다.
- 정적 import로 호환되는지 먼저 확인한다. 브라우저 전용 모듈 평가 문제가 실제로 발견될 때만 Client Component 안의 동적 import를 검토한다.
- Canvas 미지원·초기화 실패 시에도 상태 문구와 필요한 정적 대기 표시가 남아야 한다. 장식 렌더링 실패로 요청이나 화면 전체를 실패시키지 않는다.

### 4.3 테마와 토큰

- 현행 밝은 페이지에는 `theme="light"`, 검정 primary 버튼에는 밝은 잉크를 쓰는 `theme="dark"` 방향을 선택한다. **Orb의 잉크 테마는 앱 다크 모드 기능이 아니다.** OS 테마로 자동 선택하지 않고 실제 표면/variant로 결정한다.
- 색상은 실제 표면에 맞는 기존 토큰을 따른다. Canvas의 `color`는 CSS 변수 문자열을 직접 해석하지 않으므로 어댑터에서 계산된 RGB/hex 값을 전달한다. 토큰 해석 전에는 자리를 유지하고 잘못된 기본 잉크가 먼저 깜빡이지 않게 한다. 해석에 실패하면 토큰 기반 정적 표현과 문구로 폴백하며 새 색상 리터럴을 흩어 쓰지 않는다.
- 크기 20/64는 라이브러리 프리셋 선택값과 디자인 토큰을 일치시킨다. CSS transform으로 임의 확대·축소하거나 32px 프리셋을 추가하지 않는다.
- 기본 속도 1, 단색 점 표현을 유지한다. glow·그림자·커서 흡인(`gravity`)은 도입하지 않는다.

| 사용 표면             | 글자·Orb 기준 토큰                                                                        | 유지할 기존 디자인                                  |
| --------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 흰 페이지·시트        | 본문/보조 문구는 기존 `--color-text-body`/`--color-text-secondary`, Orb도 해당 계열       | 기존 h1·문구 크기·섹션 간격 유지                    |
| 회색 보조면·soft 버튼 | 버튼은 `--color-text-heading`, 작은 보조 문구는 역할에 따라 `--color-text-subtle-on-tint` | 회색 배경·모서리·기존 구분선 유지                   |
| 검정 primary 버튼     | `--color-on-primary` 또는 해당 inverse 토큰                                               | 검정 채움·흰 액션 이름 유지. 파란 CTA로 바꾸지 않음 |
| outline·danger 버튼   | heading 또는 기존 `--color-status-error`                                                  | outline 유지, danger에 빨간 채움 추가 안 함         |

20px 장식 자체를 44px 클릭 대상으로 만들지 않는다. 부모 버튼은 기존 48px/최소 44px 규칙을 유지한다. 본문 16px, 설명 최소 14px, Pretendard와 기존 line-height를 그대로 사용한다. 새 palette/font/radius/z-index는 추가하지 않으며, 필요한 신규 값은 로더 크기 토큰 두 개로 한정한다.

### 4.4 기존 공통 API 호환성

- `Skeleton`은 기존 `variant`/`count`·DOM 자리·기본 pulse를 유지한다. 선택형 `animated={false}` 같은 확장으로 Orb와 같은 영역에서만 정적으로 만든다. 모든 Skeleton 안에 Orb를 자동 삽입하지 않는다.
- `Button`은 기존 `variant`/`block`/`type`/`disabled`/`className`·이벤트·아이콘을 보존하고, 기본 `pending=false`에서 기존 DOM/모양/동작이 같아야 한다.
- 후속 `pending={mutation.isPending}` 사용 시에만 공통 20px Orb와 `disabled || pending` 처리를 적용한다. 권한 거절·미리보기의 disabled는 pending으로 해석하지 않는다. 버튼이 API를 호출하거나 retry를 추가하지 않는다.
- pending 전후 버튼 폭·높이·액션 이름을 유지하는 배치를 대표 버튼에서 먼저 확정한다. 원래 내용의 레이아웃 자리를 보존해도 공간이 부족하면 레이아웃을 넓혀 강행하지 않고 배치를 수정한다.
- `asChild` 링크는 Radix Slot의 단일 자식 구조·Link 의미·새 탭 동작을 유지한다. pending 전용 기능을 일반 button 분기로 제한하고 `asChild`와의 조합은 타입/사용 계약으로 금지한다. 링크의 disabled 흉내나 중복 children 삽입을 하지 않는다.
- `LoadingIndicator`는 header/main/h1/nav를 만들지 않는다. `PageFrame`·`TeamFrame`·`AdminShell` 또는 콜백의 기존 프레임 안에서 대기 콘텐츠만 표현한다.

| 팀원이 새로 만드는 영역                       | 사용할 공통 진입점                             | 통합 규칙                                                      |
| --------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| `loading.tsx`·사용자에게 보이는 Suspense 대기 | `LoadingIndicator` + 해당 화면의 정적 Skeleton | 프레임·제목·뒤로가기·자리 유지. 라우트 파일마다 공통 계약 검사 |
| 최초 Query·시트 내용 대기                     | 동일 `LoadingIndicator`                        | 기존 overlay 내부에 배치. 새 모달/전역 가림막 금지             |
| 실제 저장·제출·조회 버튼 대기                 | 공통 `Button`의 명시적 pending API             | API/권한/폼은 각 담당 코드가 유지, 시각 표현만 공통화          |
| 배경 갱신·추가 페이지·재연결                  | 같은 인라인 표현을 필요한 위치에만             | 기존 내용·스크롤·타이핑을 막지 않음                            |
| 실제 진행률·전송 실패·빈/성공 상태            | 기존 전용 표현 유지                            | 무조건 Orb로 바꾸지 않음. 문서에 사유와 위치 기록              |

웹 화면은 `@/components/ui/loading-indicator`만 import하고 npm 패키지나 내부 `loading-orb`를 직접 import하지 않는다. 어댑터는 한 파일에서 외부 라이브러리를 감싼다. 팀원은 대기 상태와 한국어 문구를 넘기며 모드/속도/토큰을 복사하지 않는다. 한 곳을 고치면 이 진입점을 사용하는 화면의 시각 표현에 함께 반영된다.

**문서와 검사도 공통 기반의 일부로 함께 배포한다.**

1. 프론트 AGENTS에 공통 import·pending·예외 규칙을 짧게 추가하고, 청사진 §3-4/5-2에 route/Suspense/Query/button 사용 예시를 제공한다.
2. ESLint에서 외부 패키지와 내부 어댑터의 직접 import/re-export를 허용 파일 밖에서 제한한다. 동적 import·require 우회도 검사 범위에 넣는다.
3. 기존 Vitest 탐색 범위 `src/**/*.test.{ts,tsx}` 안의 계약 검사로 기존/새 `app/**/loading.tsx`가 공통 진입점을 사용하는지 확인한다. alias·상대 경로를 해석하고, 정적 import만 해 놓고 렌더하지 않는 경우도 실패시킨다. TS AST 등 구조를 확인하며 단순 문자열 유무만으로 통과시키지 않는다.
4. 검사에서 대표 실패 fixture로 패키지 직접 import, 공통 로더 누락, 이름만 import한 미사용을 실제로 거절하는지 확인한다. 특수 예외가 필요하면 파일·이유·담당·제거 조건이 있는 제한된 목록으로 관리한다. 상태 문구 전체나 Skeleton 사용 자체를 일괄 금지하지 않는다.
5. 기존 CI가 실행하는 `pnpm lint`/`pnpm test`에 연결한다. 새 검사를 로컬 스크립트로만 남기지 않는다. PR 템플릿과 청사진 §14에 공통 사용·예외·화면 비교 결과를 추가한다.

이 검사는 외부 라이브러리 우회와 라우트 로딩 누락을 막는다. 임의의 모든 Query/상태 분기를 자동으로 의미 판별하는 것은 아니므로 화면 담당자의 새 pending 분기 리뷰도 완료 조건에 포함한다.

### 흐름별 보존 조건

- **페이지 이동:** 헤더·하단 메뉴·현재 화면의 제목/뒤로가기를 유지한다. root layout에서 모든 navigation을 감시해 별도 전역 로더를 추가하지 않는다.
- **목록:** `isPending` 최초 조회와 `isFetching` 배경 갱신을 구분한다. 추가 페이지 조회는 목록 끝의 작은 로더/기존 더 보기 문구를 사용하고, 목록 전체를 교체하지 않는다.
- **버튼:** 원래 액션 이름과 비활성·중복 제출 방지를 유지한다. 아이콘이 나타나도 폭·높이·접근성 이름이 튀지 않게 한다.
- **팀 생성:** 설치 미리보기에 실제 검증 중인 것처럼 로더를 붙이지 않는다. 서버 검증 단계가 생기면 해당 pending에 연결한다.
- **이슈 생성:** 기존 단계·재시도·상세 이동을 유지한다. 목업 브라우저/서버 데이터 분리로 생기는 상세 조회 오류를 로딩 애니메이션으로 숨기지 않는다.
- **채팅:** 최초 방 조회, 연결 복구, 과거 메시지 조회, 개별 전송 상태를 구분한다. 메시지마다 큰 Orb를 반복하지 않으며 전송 실패/재시도 표시는 유지한다.
- **결제:** 서버 승인 확인/화면 준비에만 붙인다. 새 로더 마운트·재렌더 때문에 승인 API를 다시 호출하지 않으며, 오류·결과 화면을 가리지 않는다.
- **업로드:** 이미 실제 업로드 진행률이 있으면 그 수치와 파일별 오류를 유지한다. Orb를 퍼센트처럼 사용하지 않는다.

`role="status"`의 “혜택이 적용됐어요”, “지금은 대화를 읽을 수만 있어요”, 안 읽은 메시지 수 등은 로딩이 아니다. 로딩 관련 검색 결과를 일괄 치환하는 방식으로 수정하지 않는다.

## 6. 접근성·성능 기준

아래는 전체 도입 품질 기준이다. 실제 완료 범위와 기기/성능 미검증은 §12에 기록하며, 부분 검증으로 전체 항목을 체크하지 않는다.

- [ ] 로딩 문구는 각 화면의 기존 한국어 문구를 재사용한다. 패키지 기본 영문 `Composing…`를 사용자 상태 문구로 노출하지 않는다.
- [ ] Canvas는 장식으로 `aria-hidden` 처리하고 상태 문구 한 곳에서만 `role="status"`/polite 알림을 제공한다. 이미 live region이 있는 콜백·시트에서는 중복을 피한다.
- [ ] 콘텐츠 영역의 `aria-busy`와 상태 알림의 위치를 분리해 알림이 busy 때문에 끝까지 보류되지 않는지 검증한다. `aria-busy`만으로 화면 조작 차단을 대신하지 않는다.
- [ ] OS 줄인 모션에서는 정적 프레임을 유지하고 설정 변경도 반영한다. 기존 MotionConfig/CSS 규칙만으로 Canvas 루프가 멈춘다고 가정하지 않는다.
- [ ] 장식에 포커스·탭 정지를 추가하지 않는다. 확대 200%, 좁은 화면, 긴 한국어 문구에서도 잘리지 않는다.
- [ ] 화면 밖·백그라운드·언마운트에서 rAF/observer/listener가 정리되거나 중단되는지 확인한다. 공유 시계를 쓴다는 것과 rAF 루프가 하나라는 것은 다르다.
- [ ] 한 화면의 큰 로더는 주 대기 영역 하나로 제한하고 가상 목록/채팅 항목별 Canvas 반복을 피한다.
- [ ] 기존 한국어 문구는 정상 텍스트 대비를 유지한다. 밝은 배경·soft 배경과 줄인 모션 정적 프레임에서 시각적 식별을 확인한다.
- [ ] Next 빌드 전후 라우트 JS/gzip 증가량과 대표 화면 CPU/프레임을 측정해 PR에 기록한다. npm 파일 크기로 성능 합격을 선언하지 않는다.
- [ ] 현재 디자인 토큰 값·전역 CSS·프레임·헤더/GNB·라우팅/overlay/query key는 로더를 위해 바꾸지 않는다. 예외가 필요하면 별도 원인·설계 차이를 먼저 기록하고 로딩 PR에 섞지 않는다.
- [ ] 이전/이후의 로더가 없는 정상·오류·빈 화면은 같은 크기/색/여백을 유지한다. 로딩 중에도 버튼 크기·카드 자리·본문 가로 넘침·메뉴 위치가 달라지지 않는다.

## 8. 충돌을 줄이는 구현·팀 통합 절차

### 8.1 변경 묶음과 파일 경계

최신 dev 대조 후 사용자가 전체 구현을 요청해 같은 기능 브랜치에서 공통 기반→화면 적용→검증 순으로 진행했다. 초기의 여러 PR 분리안은 공통 기반과 적용/문서 커밋을 구분하는 방식으로 조정한다. 아래 파일 경계를 유지하고 최종 통합 검사를 함께 수행한다. dev 직접 커밋·자동 병합·운영 배포는 하지 않는다.

| 묶음        | 포함                                                                                      | 포함하지 않을 것                                        |
| ----------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 공통 기반   | 패키지/lock, 로더·선택형 Button/Skeleton 확장, 토큰 두 개, lint/계약 검사, 규칙·예제 문서 | 페이지 기능·API·GNB·팀/운영 레이아웃 리팩터링           |
| 대표 화면   | A 로그인 콜백, E 피드의 대기 표현만                                                       | 콜백 요청/returnTo, 피드 추천/페이지 조회 로직 수정     |
| 담당별 적용 | A~E 페이지의 로딩 분기·필요 import·로더 전용 배치만                                       | 담당자가 진행 중인 비즈니스 로직·mock 계약·쿼리 키 변경 |
| 최종 통합   | 누락/예외 목록, 시각/상태 회귀 결과·팀 사용 안내                                          | 서버 설정·새 라이브러리 교체·미완료 기능까지 성공 처리  |

공통 계약과 검사 강제 시점도 순서를 맞춘다. 기반 PR에서는 기존 32개 파일을 **이행 대상 목록**으로 명시하고 새 로딩 파일의 누락·직접 패키지 사용을 막는다. 담당별 전환 때 항목을 제거하며 목록이 새 누락을 숨기도록 늘어나지 않게 검사한다. **최종 완료 시 이행 예외는 0개**여야 한다. 설계상 유지하는 실제 진행률 등은 별도의 사유 있는 예외로 구분한다. 공통 PR만 반영해 기존 화면 전체 CI가 곧바로 깨지는 전환은 피한다.

### 8.2 공통 파일 동시 수정 방지

- 구현을 시작할 때 최신 기준과 해당 파일의 미병합 작업 여부를 확인하고, E의 공통 UI·C의 테스트·각 화면 소유자를 PR 리뷰 경계에 표시한다. 담당 변경이나 팀원 브랜치 직접 수정은 하지 않는다.
- Button/Skeleton/토큰/ESLint/가이드의 공통 API는 기반 묶음에서 확정한다. 페이지별 묶음에서 같은 API를 각자 다시 설계하지 않는다.
- 기존 토큰 **이름·값**, Button의 기존 variant, Skeleton 기본 동작을 바꾸지 않는다. 새 토큰은 해당 파일에 추가하며 다른 구역을 재정렬하지 않는다.
- 공통 프레임·페이지 전체 포맷 변경과 import 정리, 관계없는 코드 정돈은 섞지 않는다. 수정한 문서/파일만 포맷한다.
- merge 충돌이 생기면 양쪽 의도와 최신 계약을 대조한다. `ours/theirs`로 통째로 덮거나 팀원 변경을 버리지 않는다. 의미를 확인할 수 없는 충돌은 해당 묶음을 멈추고 리뷰할 수 있는 차이로 정리한다.
- manifest 충돌은 양쪽 새 의존성을 보존해 해소한 뒤 동일 pnpm 10.15.0으로 lock을 맞춘다. 필요 시 lockfile-only 갱신을 사용하되 기존 lock을 삭제하지 않는다. 관련 importer·해결 항목 외 버전이 바뀌지 않았는지 확인하고 frozen 설치로 마무리한다.
- 충돌 해소 후에는 Git 표식 제거뿐 아니라 관련 단위/계약 검사, frozen 설치, 최종 시각 비교도 다시 수행한다. 강제 push·브랜치 삭제·reset으로 해결하지 않는다.

팀원에게 자동 반영되는 범위는 **통합된 공통 코드를 사용하는 웹 화면**이다. 팀원이 오래된 커밋에서 계속 개발하거나 전용 로더를 복사하면 공유되지 않으므로 기준 반영·frozen 설치·공통 진입점·CI 검사를 함께 운영한다. Expo는 웹 URL의 새 빌드를 받아 같은 효과를 쓰며, 로컬 개발 URL을 보는 앱은 해당 로컬 코드/의존성이 갱신돼야 한다.

## 9. 디자인·기능을 보존하는 합격 기준

### 9.1 비교 방법

구현 전 기준 커밋의 동일 화면·계정·데이터·viewport에서 캡처와 요소 위치/크기를 기록한다. 느린 요청은 테스트에서 제어하고 성공/오류/빈 결과를 각각 만든다. 비교 캡처에서는 reduced motion으로 Orb/Skeleton의 움직임을 고정하며 캡처 안정화를 위해 제품 응답 시간을 늦추지 않는다.

| 비교 영역                | 합격 기준                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 정상·빈 화면·오류/재시도 | 로더가 남지 않고 기존 문구·버튼·글꼴·색·카드 배치가 동일. 의도하지 않은 시각 차이 0건                                                                                     |
| 로딩 자리                | 기존 Skeleton 개수/variant/위치와 부모 콘텐츠 크기 유지. status 선언이 없는 13개도 기존 aria-label/문구를 먼저 대조하고, 상태 행이 없는 화면에는 새 큰 행을 추가하지 않음 |
| 버튼                     | primary/outline/soft/danger × block/자동 폭 × 기존 아이콘 × 긴 한국어 × pending 전후의 크기/탐색/접근성 이름 유지                                                         |
| 프레임                   | `PageFrame`/TeamFrame/AdminShell, h1·랜드마크·메뉴·뒤로가기 props 동일. 스크롤/초점·safe area 침범 없음                                                                   |
| GNB/반응형               | 360/600/639/640/1024/1280/1440px, 200% 확대에서 새 가로 넘침·메뉴 이동 없음                                                                                               |
| 시트                     | 기존 제목·버튼·높이 제한·닫기/뒤로가기/초점 복귀 유지. 로딩 때문에 새 overlay/history 항목 없음                                                                           |
| 테마·접근성              | 흰/회색/검정 CTA에서 식별 가능, 기존 대비/색 역할 유지. 상태 알림 1곳·줄인 모션·키보드/axe 회귀 없음                                                                      |

원래 프레임 구조가 다른 운영 페이지에 `PageFrame`을 새로 덧씌우지 않는다. 64px 공간이 안 맞으면 작은 크기/기존 자리 배치를 사용하고, 문서로 정한 디자인을 바꿔 맞추지 않는다. 비활성 버튼의 기존 스타일도 임의로 바꾸지 않으며 필수 진행 안내는 읽을 수 있는 상태 문구로 제공한다.

스크린샷은 변경 의도가 있는 로더 영역만 차이를 허용하고 정상 화면 전체·버튼·GNB를 무더기로 mask하거나 baseline 전체를 자동 승인하지 않는다. 시각 비교와 요소 크기/초점/의미 검사를 함께 수행한다. 기존 문제를 발견하면 별도 기록하고 이번 변경의 새로운 회귀와 구분한다.

### 9.3 중단·복구 기준

- [x] pnpm frozen 설치, lint/타입/단위/빌드와 공통 사용 계약 검사가 통과한다.

실패한 적용 묶음은 완료로 처리하지 않는다. 미검증 기기·성능 항목은 §12에 명시하고 해당 환경의 검증을 도입 코드 완료와 구분한다. Canvas 지원/성능 문제가 있으면 공통 어댑터에서 정적 표시·문구로 폴백하고, 여러 페이지를 역수정하거나 제품 API를 바꿔 우회하지 않는다. 필요 시 기존 표현으로 되돌리는 별도 수정 PR로 처리하며, 강제 push/reset·운영 롤백을 이 계획 작업에서 실행하지 않는다.

### 12.2 확정된 구현과 팀 공통 계약

- 웹에만 `thinking-orbs@0.3.2`를 정확한 버전으로 추가했다. manifest와 단일 pnpm lock의 해당 항목만 변경했으며 React/Next/pnpm/네이티브 의존성은 올리지 않았다. MIT 고지는 `frontend/THIRD_PARTY_NOTICES.md`에 보존했다.
- `LoadingIndicator`가 Server에서도 쓸 수 있는 공개 진입점이고, `LoadingOrb`만 Client Canvas를 담당한다. `state="composing"`, `speed={1}`, inline 20px/block 64px로 고정한다. 색상은 기존 본문·inverse·danger 토큰에서 계산한다.
- Canvas가 없거나 잉크를 해석하지 못하거나 장식 렌더러가 실패하면 정적 점선 표시와 한국어 문구를 유지한다. 장식 오류 경계가 페이지나 요청 처리를 대체하지 않는다.
- 기존 스켈레톤의 모양·개수는 그대로 두고, 공통 영역 안의 pulse만 끈다. Orb는 이미 확보된 자리 위에 배치한다. 기존에 문구 행이 없던 자리는 `labelHidden`으로 높이를 유지한다.
- Button의 기본 자식 구조·스타일·링크 의미를 유지한다. 명시적인 `pending`에서만 원래 액션 이름의 자리를 남기고 Orb를 겹치며 중복 클릭을 차단한다. `pendingLabel`은 busy 버튼 바깥의 숨긴 상태 알림으로 제공한다. `asChild`와 pending 조합은 타입으로 금지한다.
- 앱/feature 기준 **32개 route fallback, 48개 화면 내부 placeholder 영역, 13개 작은 상태 표시, 48개 Button pending 사용처**를 반영했다. 공통 ConfirmDialog에도 적용해 기존 삭제/차단/탈퇴 등의 확인 대기를 재사용한다.
- 반복 목록의 프로젝트 추가·차단 해제·채팅 요청 수락과 결제 상품은 현재 mutation의 대상에만 Orb를 표시한다. 다른 항목의 기존 disabled 처리는 유지한다.
- ESLint가 외부 패키지·내부 어댑터 직접 import/re-export와 리터럴 dynamic import/require를 제한한다. Vitest AST 계약은 모든 기존/새 `loading.tsx`가 공통 컴포넌트를 실제 JSX에 사용하는지 검사한다. 의미를 자동 판단할 수 없는 화면 내부 분기는 담당자 리뷰도 필요하다.

### 12.5 성능 수치와 미검증 범위

빌드 비교는 `.next/static/chunks/*.js` 전체 파일의 원본 크기 합과 각 파일을 gzip한 크기의 합이다. 최초 기준은 79개 파일/2,419,896B raw/798,790B gzip이다. 최종은 79개 파일/2,456,522B raw/812,770B gzip이며, 증가량은 raw +36,626B / gzip 합 +13,980B다. 이는 개별 라우트의 전송량이나 vendor 단독 용량이 아니며, CPU/FPS 합격의 근거로 사용하지 않는다.

실제 iOS Safari·Firefox·Expo Android/iOS WebView 기기, 저사양 CPU/FPS·장기 메모리, 실제 기기 200% 확대, 모든 32개 라우트의 느린/오류/빈 상태 조합, 실제 GitHub/인증/결제 서버 연동, 다른 팀원의 독립 작업 브랜치 설치는 미검증이다. 공통 폴백과 Chromium 증거를 넘어 이 환경까지 완료로 표시하지 않는다. 실제 기기 배포 전에는 해당 환경 검증이 필요하다.

기능 브랜치에서 검증용 서버만 실행했으며 제품 테스트 페이지·새 API·배포·dev 자동 병합은 추가하지 않았다. `frontend-loading` CI는 별도 mock 서버와 브라우저 fixture를 사용하고 ci-result에 포함된다. README·AGENTS·청사진·디자인·PRD·TODO·WBS·B 계획의 공통 로딩 안내도 함께 갱신했으므로 외부 한국어 원본에도 해당 변경을 동기화해야 한다.
