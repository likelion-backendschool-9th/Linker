# 4단계: 정리와 팀 결정 사항

상태: 시작 전 (팀 결정 필요 항목 포함)

대상 독자: 팀 전체(결정) + 실행 담당자. 코드보다 팀이 정해야 하는 항목이 많다. 각 항목은 "현재 상태 → 선택지 → 제안" 순서로 적었다.
기준: 1단계 PR #244, CI 규칙 PR #245가 `dev`에 머지된 상태.

> 수치는 2026-11-06 조사값이다. 실행 전에 다시 확인한다.

## 1. README

원래 계획(초기 계획): **README 다시 쓰기** — 대표 이미지, 만든 이유, 해결하는 문제, 시연 GIF, 배포 링크, 실행 방법.

현재: 루트 `README.md`가 이미 있다. 서비스 개요, 흐름 다이어그램(mermaid), 기능별 경로 표가 있다. 위 항목 중 없는 것이 무엇인지 확인한다.

할 일
- 원래 계획 항목을 채운다: 대표 이미지, 만든 이유, 해결하는 문제, 시연 GIF, 배포 링크, 실행 방법. 시연 GIF·이미지는 용량이 크므로 저장소에 넣을지 외부 링크로 둘지 정한다(저장소 용량·`docs/` 번역 규칙과 무관한 자산이다).
- 추가로 확인할 것: 환경 변수, 기술 스택, 폴더 구조, 브랜치/커밋/PR 규칙 링크(AGENTS.md "Git workflow"), 팀 구성과 역할.
- 1단계 이후 달라진 내용 반영: 컨트롤러·서비스 이름 규칙, `/api/v1` 전역 접두어, `entity/type/`, `pnpm install` 시 훅 설치.
- `docs/` 문서 링크가 현재 구조와 맞는지 확인한다.
- 에이전트 표시는 넣지 않는다.

제안: 위 항목 점검 후 필요한 부분만 고치는 `docs:` PR 하나.

## 2. 각자 Fork + 개인 README, 개인 GitHub 프로필

원래 계획(초기 계획)
- **각자 Fork + 개인 README**: 내가 맡은 부분과 기여한 내용을 정리한다.
- **개인 GitHub 프로필**: Pin 고정, 자기소개, 사진.

개인 작업이라 각자 진행한다. 팀은 형식(맡은 영역, 기여 내용, 주요 PR 링크, 시연 링크)만 공유하면 된다. 팀 저장소의 README는 포트폴리오용이라 이 내용과 겹치지 않게 한다.

현재: 저장소는 조직(`likelion-backendschool-9th`) 소유다. 조직 프로필(`.github` 저장소의 `profile/README.md`)이 있는지는 아직 확인하지 않았다.

선택지
- 조직 프로필 README: 팀/서비스 소개, 대표 저장소 링크. 조직 관리자 권한이 필요하다.
- 팀원 개인 프로필 README: 각자 `<아이디>/<아이디>` 저장소에 작성.
- 저장소 소개(About)와 토픽 설정.

제안: 저장소 About(설명, 토픽, 배포 URL)을 먼저 정리하고, 개인 Fork README와 프로필은 각자 처리한다. 조직 프로필은 선택 사항이라 팀이 정한다.

## 3. PR 라벨·Assignee 채우기 (과거 PR)

현재(조사 시점): 전체 PR 152개(머지 148, 닫힘 3, 열림 1). 이 중 **Assignee 없음 145개, 라벨 없음 6개**.
- 라벨은 `labeler` 워크플로(경로 기준 `frontend`/`backend`/`docs`)와 타입 라벨(`feat`/`fix`/`chore`)이 있다. 타입 라벨을 제목으로 자동 부여하는 워크플로는 없다.
- Assignee 자동 지정은 #245 이후 PR부터 적용된다. 과거 PR은 비어 있다.

할 일
- 과거 PR에 Assignee를 작성자로 채운다. 스크립트 예: `gh pr list --state all --json number,author,assignees` → 비어 있는 PR에 `gh pr edit <번호> --add-assignee <작성자>`.
  - 닫힌·머지된 PR도 수정 가능하다. 작성자가 협업자가 아니면 지정이 안 된다(그 경우 건너뜀).
- 라벨 없는 PR 6개는 경로/제목 기준으로 수동 또는 스크립트로 채운다.
- 앞으로의 PR을 위해 제목 type(feat/fix/chore/docs)을 라벨로 자동 부여하는 워크플로를 추가할지 정한다(선택).

주의: 일괄 수정은 되돌리기 번거롭고 알림이 많이 발송될 수 있다. 소량으로 먼저 시험하고, 팀에 알린 뒤 실행한다. 수정 대상 목록을 먼저 파일로 만들어 검토한다.

## 4. 과거 공동 작성자 줄 처리

원래 계획(초기 계획): "이미 들어간 Claude 공동 작성자 줄(커밋 56개): 지우려면 히스토리를 다시 써서 강제 push해야 해요. 팀원 전원의 로컬 저장소에도 영향을 주니, 할지 말지는 팀이 정해야 해요. 최소한 앞으로는 넣지 않으면 돼요."

현재(`git log --all` 조사, 2026-11-06)
- `Co-authored-by` 에이전트 줄이 있는 커밋: **합계 53개** — Claude 17개(`origin/main`에 1개 포함), Cursor 36개. 원래 계획의 56개는 더 이른 시점 수치로 보인다. 실행 직전에 다시 센다.
- 커밋 작성자별(에이전트 줄이 있는 커밋): 이준호 24, Yunsu0407 12, OMS-cc 11, JUNHORANG 4, OMS 2. 팀원 모두의 커밋에 걸쳐 있다.
- `Generated with Claude` 문구는 없다.
- 전체 커밋 수 192개(모든 ref).
- **"최소한 앞으로는 넣지 않으면 된다"는 이미 처리됐다**: AGENTS.md 규칙, CI `pr-rules`(#245), `commit-msg` 훅 확장.

선택지

| 선택 | 방법 | 영향 |
| --- | --- | --- |
| A. 그대로 둔다 | 아무 것도 하지 않는다 | 기록 보존, 기여자 목록에 Claude/Cursor가 표시될 수 있다 |
| B. 히스토리를 다시 쓴다 | `git filter-repo --message-callback`으로 trailer만 제거 후 `dev`/`main`에 강제 푸시 | 모든 커밋 해시가 바뀐다. 팀원 전원이 다시 클론/리셋해야 한다. 열린 PR·브랜치가 깨진다 |
| C. 새로 시작 | 현재 상태를 새 저장소로 이전 | 가장 단순하지만 이슈·PR 기록이 사라진다 |

판단 기준
- B는 AGENTS.md에서 "파괴적 작업은 사용자 명시 승인 필요"로 규정한 강제 푸시를 포함한다. 팀 전체 합의 없이는 하지 않는다.
- 기여자 목록 노출만 문제라면 A가 가장 안전하다. GitHub의 기여자 표시는 `Co-authored-by` trailer 기준이므로 그 줄이 보이는 것이 문제인지 먼저 확인한다.

제안: 영향을 팀에 공유하고 A와 B를 결정한다. B로 간다면 다음 순서를 지킨다.
1. 모든 열린 PR을 머지/정리하고 작업을 멈춘다(동결 시간 공지).
2. 저장소 전체 미러 백업(`git clone --mirror`)을 만든다.
3. 사본에서 `git filter-repo`를 실행하고 메시지 변경만 되었는지 diff로 검증한다.
4. 보호 브랜치 설정을 일시 해제하고 강제 푸시한다(승인된 사람만).
5. 팀원이 새로 클론하거나 `git fetch && git reset --hard origin/<브랜치>`로 맞춘다.
6. 보호 규칙을 복구하고 `pr-rules`를 Required status check로 다시 설정한다.

## 5. 추가 설정 (3단계 이후 남는 항목)

- GitHub Settings에서 `pr-rules` 체크를 **Required status check**로 지정한다(미지정이면 규칙 위반 PR도 머지된다). 팀 합의 후 설정.
- 팀원에게 `dev`를 받고 `frontend`에서 `pnpm install`을 한 번 더 실행해 commit-msg 훅을 설치하게 안내한다.
- 훅은 로컬 편의 기능이고 강제는 CI다. 훅을 안 써도 CI가 막는다.
