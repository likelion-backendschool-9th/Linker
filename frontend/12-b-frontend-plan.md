> 기준: `origin/dev` = `8a651193fe99d518c7c2dfb9e5fb2b915cf834c2`
> 현재 단계는 **B 담당 프론트 화면 구현**이다. 작업 브랜치는 `feat/b-frontend-ui`이며, 실제 저장·가입·제재·결제와 백엔드 구현은 이번 범위에서 제외한다. 아래 기능 완료 조건은 후속 연동 단계까지 포함한 목표이며, 이번 화면 구현만으로 완료 처리하지 않는다.

## 1. 작업 범위와 Git 보호

- 사용자 담당은 **B의 프론트엔드**다. WBS의 기존 풀스택 배정표에서 백엔드 업무를 이번 범위로 가져오지 않는다.
- 앞선 계획 단계에서는 이 문서만 추가·갱신했다. 현재 화면 구현 단계는 사용자 요청에 따라 새 `feat/b-frontend-ui` 브랜치의 B 담당 프론트 소스와 필요한 공통 연결 지점으로 한정한다. 백엔드·팀원 브랜치·기존 미추적 `.vscode/`는 보존한다.
- **사용자가 보호 대상으로 정정한 브랜치는 `dev`다. 로컬 `dev`와 원격 `dev`를 변경하지 않는다.** `develop`을 보호하는 것으로 잘못 해석하지 않는다.
- `dev`/`main`을 작업 대상으로 체크아웃하거나 그 브랜치에서 pull·수정·커밋·푸시·머지·삭제하지 않는다. 저장소의 일반적인 “dev 전환 → pull” 절차보다 이번 사용자 지시가 우선한다. 기준 브랜치의 내용·커밋 조회는 읽기 전용으로 한다.
- 계획 브랜치는 최초 확인 시 `fetch` 후 `origin/dev`에서 만들었으며 로컬 `dev`에는 `pull`하지 않았다. 구현 브랜치도 같은 기준 커밋에서 분기했고 `dev`의 커밋·파일은 갱신하지 않았다.
- 원격 팀원 브랜치는 `git show`/`git diff`로 읽기만 한다. 팀원 브랜치의 체크아웃·수정·머지·cherry-pick은 하지 않는다.
- 이번 프론트 화면 작업은 하나의 범위로 `feat/b-frontend-ui`에서 진행하고, 후속 실제 기능 연동은 페이지 단위 `feat/*` 브랜치로 분리한다. 최초 작업에서는 커밋·푸시·PR 생성·머지를 진행하지 않았다. 2026-11-02 사용자의 최신 `dev` 반영 요청에 따라 현재 작업을 로컬 커밋으로 보존하고 원격 `dev` 변경을 **현재 작업 브랜치에만** 통합한다. 푸시·PR 생성·`dev`로의 머지는 진행하지 않는다.
- 공통 연결은 기존 팀 헤더의 팀 전환 버튼, 채팅의 PR 진입·카드 표시, 오버레이 키와 통계 기간 상수로 최소화한다. 공통 인증·채팅 송수신·GNB의 디자인과 기능은 재설계하지 않는다.

충돌은 문서별 권한에 따라 판단한다. 정책의 숫자·권한, TODO의 URL·화면, WBS의 엔드포인트가 우선이다. 백엔드 청사진의 BFF 구조는 **제안**이며, 현재 `apiFetch`와 Nginx의 `/api/v1/*` 흐름을 이번 작업에서 BFF로 바꾸지 않는다. JWT는 httpOnly 쿠키에 유지하고 GitHub 토큰·JWT를 프론트나 브리지로 전달하지 않는다.

- PRD의 P0/P1, TODO/WBS의 Required/Included, ERD의 필수/포함 테이블 표시는 서로 다른 분류다. 이를 하나의 우선순위로 바꿔 읽지 않는다.
- Included를 뒤로 미루는 순서와 실제 출시 조건은 다르다. WBS의 이연 순서만으로 MVP의 데모·출시 조건을 충족했다고 판단하지 않는다.
- 약관·개인정보 문서는 영문 참고 번역이자 초안이다. 법률 검토나 빈 항목의 결정을 이번 프론트 작업에서 대신하지 않으며, 사용자에게 약관 본문을 표시할 때는 한국어 원본을 사용한다.
- 초기 설정 가이드의 GitHub 설정 변경·라벨 생성·전역 Git 설정·브랜치 정리 명령은 참고 절차다. 문서를 읽었다는 이유로 실행하거나 팀 저장소 설정을 바꾸지 않는다.

| 문서 간 차이 | 이번 계획의 처리 |
| --- | --- |
| 루트 지침은 “5 STOMP destinations”라고 요약하지만 WBS는 `/ws` 연결 1개 + SEND 1개 + SUBSCRIBE 3개로 설명한다. | 신규 경로를 만들지 않는다. 실제 계약은 WBS의 연결 1개·STOMP 목적지 4개, 총 5개 실시간 경로를 따른다. |
| 정책 §6은 팀 member의 GitHub 조직 초대를 허용하지 않지만 WBS 09는 `team MEMBER + org owner`로 적고 있다. | 단순히 조직 오너라는 이유로 member 버튼을 열지 않는다. 정책에 맞는 owner/admin + GitHub 조직 오너 범위로 화면을 계획하고, member 예외는 백엔드 담당과 권한 계약을 확인할 때까지 미확정으로 남긴다. |
| 백엔드 청사진의 오류 표 일부는 `PLAN_LIMIT`을 429, `GITHUB_PERMISSION`을 외부 장애와 묶는다. 다른 원문에는 403 또는 별도 의미로 쓰인다. | 임시 HTTP 번호만으로 분기하지 않는다. 기존 `ApiError`와 오류 `code/detail`을 사용하며 최종 HTTP 상태는 WBS·정책과 대조한 OpenAPI로 확정한다. |
| 백엔드 청사진은 쿠키/BFF의 대안을 미확정으로 열어 두지만 루트 지침은 부모 도메인 httpOnly JWT를 고정한다. | 고정 지침과 현재 프론트 구조를 따른다. B의 페이지 구현에서 인증 방식·BFF·STOMP 인증 티켓을 새로 도입하지 않는다. |

정책·화면·API를 새로 정하지 않는 계획이므로 원문 기획 문서와 기존 총계(33페이지·40컨트롤러·204 REST·69테이블)를 수정하지 않는다. 향후 실제 계약 변경이 필요하면 해당 담당자와 먼저 정리하고 한국어 원본의 동기화 항목도 보고한다.

### 3.3 재사용할 디자인

- 흰 배경, 검정 기본 CTA, 회색 보조 영역, 얇은 테두리, Pretendard를 유지한다. 파란색은 가이드가 허용한 강조에 사용하고 CTA 배경으로 쓰지 않는다.
- 색·글자 크기·간격·모서리는 `src/styles/tokens/`의 CSS 변수만 사용한다. 신규 토큰이 필요하면 공통 디자인 변경 항목으로 분리한다.
- 07의 팀 카드와 10의 초대 미리보기는 기존 카드 모양과 동일하게 구성한다. 09는 기존 `TeamFrame`과 팀 메뉴 안에 설정 섹션을 넣는다.
- 세그먼트는 기존 회색 트랙·흰 선택 항목을 따른다. 그림자는 `--shadow-segment-active` 외에 추가하지 않는다.
- 앱 화면은 360px부터 구성하고 600/1024px에서 확장한다. `--content-max-width`, `--page-gutter`, 기존 하단 메뉴와 safe area를 따른다.
- 26은 1024px 이상에서 회원 목록 + 상세 패널, 좁은 화면에서는 상세 시트로 구성한다. 27은 필터 + 읽기 전용 표를 중심으로 구성한다.

| COMPLETED | 채팅·이슈는 계속 사용하고 새 모집 글은 만들지 않는다. 7일 내 완료 취소와 확정 후 다시 시작을 구분한다. |
| READ_ONLY | 기존 채팅·이슈 조회와 재설치 안내를 제공한다. 설정의 변경 액션은 차단한다. 30일 후 보관 전환은 서버 응답으로 반영한다. |
| ARCHIVED | 워크스페이스의 보관 그룹과 채팅 기록 조회를 제공한다. 활동 팀 수에서 제외하고 활동 화면·쓰기 기능을 임의로 복원하지 않는다. |
| DELETED | 팀에서 이탈하고 멤버에게 알림을 제공하는 서버 흐름을 따른다. 채팅은 30일 후 삭제되며 GitHub 조직·이슈는 남는다는 정책을 안내한다. |

팀 밖 사용자에게 Operator 역할만으로 접근을 허용하지 않는다. 정지 계정의 조회 허용과 변이 금지도 팀 역할과 별도로 적용한다. 완료 기록의 14일 소속 조건·7일 확정 및 탈퇴자의 미완주 계산은 서버 결과를 표시하고, 분모가 0인 완료율이나 재시작 시 계산 방식은 임의로 정하지 않는다.

완료: 역할 × 팀 상태 × 플랜별 허용/금지, 초대 폐기, 조직 초대 한도 오류, 수신 전 소유권 유지와 수락 후 역할, 청구 관리자 유지, 완료 취소 기한, 완료 팀의 채팅 유지, 삭제 이름 확인, 변이 후 관련 캐시 갱신을 검증한다.

### 10 초대 수락 — Required

완료: `demo-expired/revoked/member/full/limit`와 정상 미가입 사용자의 수락, 로그인/온보딩 복귀, 중복 제출 방지, 팀/채팅 참여 반영을 확인한다.

### 17 PR 연동 — Required, D와 경계 확인

완료: 네 이벤트, 목록 필터, 빈/실패 상태, 레포별 동일 번호 구분, 개인 채팅에서 PR 기능 미노출, 재연결 후 중복 없음과 시트 뒤로가기를 확인한다. 실 GitHub 웹훅 검증은 백엔드 통합 시 별도다.

### 26 운영 회원 관리 — Required

1. `(admin)/admin/users`에 검색·상태·회원 유형·확인 필요 필터를 URL 상태로 제공한다. 기존 `AdminShell`과 A의 25 운영 진입/OTP를 차용한다.
2. 상세에 마스킹 이메일·제재/신고 이력·구독/결제, recruiter의 회사·도메인·직무·최근 30일 제안 집계를 표시한다. 일반 회원 화면에 이 정보를 노출하지 않는다.
3. 제재 사유 입력, 경고/7일/30일/영구 정지, 리드 전용 해제 확인, 사유 입력 후 이메일 열람을 시트로 구현한다. 환불은 Included로 분리한다.
4. 상세·검색·계정 변경 시 전체 이메일과 민감한 상세 캐시를 정리한다. 이메일을 URL·토스트·로그에 넣지 않는다. OTP 확인 전 상세를 prefetch하지 않는다.

운영자에게도 신고되지 않은 팀·1:1 대화 전체를 열어주지 않는다. 신고 내역에서 대화를 확인할 필요가 있으면 A의 25에서 신고 당시 복사된 대상 메시지와 앞뒤 10개 범위만 차용한다. Recruiter 정지 후 광고가 자동 복원된다고 표시하지 않으며 운영자가 해제하는 서버 정책을 따른다.

완료: 비운영자 404, OTP 전 데이터 요청 방지, 일반/리드 액션 구분, 사유 누락 차단, 제재/이메일 열람 후 27 기록 반영, 작은 화면 시트 및 키보드 조작을 확인한다. 30분 idle 처리의 서버 보장은 별도 통합 검증이다.

### 27 조치 기록 — Required

운영자·조치 유형·KST 기간 필터와 운영자/시간/대상/행위/사유를 표로 제공한다. 좁은 화면의 표 영역은 독립 스크롤/읽기 순서를 유지하며 본문 전체 가로 넘침을 막는다. 검색 결과 없음·로딩·오류/재시도·더 보기를 처리한다. 수정·삭제 버튼은 없다.

완료: 필터 URL 유지, 날짜 경계, 조치 후 기록 갱신과 최신순, 접근 권한, 표의 caption·열 머리글을 확인한다.

### 30 내 통계 — Included

1. `(developer)/me/stats`에 본인 게시물별 좋아요·댓글·조회 수를 제공한다.

### 00 후반 sitemap 연결 — 공개 데이터 계약 후

- 게시물·모집 글·개발자 프로필의 공개 URL만 kind별 API에서 받아 분할 sitemap으로 구성한다. 모집 글은 열림 상태만 sitemap에 넣되, 마감된 글의 index 가능 여부와 혼동하지 않는다.
- 숨김·삭제·정지·탈퇴 대기·recruiter 프로필을 제외하는 것은 서버 계약으로 확인한다. 초대·팀·채팅·운영·통계 URL은 sitemap에 넣지 않는다.
- 청사진 §8의 시작·법적 문서·피드·팀 찾기 등 정적 공개 경로도 확인한다. `robots.ts`의 sitemap URL과 실제 생성 경로를 맞추고 쿼리 매개변수를 제거한다.
- 쿠키 없는 공개 요청에만 하루 캐시를 적용한다. 개인 팀 목록·통계 응답을 sitemap 생성에 재사용하지 않는다. 실제 API가 준비되기 전에는 목업의 임의 id를 공개 URL로 발행하지 않는다.

완료: kind별 URL·페이지 분할·제외 조건·canonical을 확인하고 `robots.ts`의 sitemap 주소가 실제 결과를 가리키는지 검증한다. 개인 데이터와 미연동 목업 URL이 출력에 섞이지 않아야 한다.

## 8. 파일 배치와 공통 변경 경계

```text
frontend/apps/web/src/
  app/(developer)/workspace/                # 07: page, loading, _components, _lib
  app/(developer)/teams/new/                # 08: 단계 폼, callback, _lib
  app/(developer)/teams/[id]/settings/      # 09: 설정 섹션과 시트
  app/(developer)/teams/[id]/_components/   # 기존 팀 틀, 전환 시트의 연결 지점
  app/(public)/invite/[code]/              # 10: 미리보기, 수락 클라이언트, metadata
  app/(member)/chats/[roomId]/_components/  # 17: D와 PR 전용 컴포넌트 연결
  app/(admin)/admin/users/                 # 26: 목록·상세·조치 시트
  app/(admin)/admin/audit/                 # 27: 필터·기록 표
  app/(admin)/admin/_components/           # 25/26 공통화는 A의 통합 후 실제 재사용 때만
  app/(developer)/me/stats/                # 30: 통계 영역·차트·표
  features/teams/                          # 그룹을 넘는 07–10의 실제 공통 기능만
  mocks/pages/p07-*, p08-*, p09-*, p10-*   # 기존 파일 보완은 구현 단계에 한정
  mocks/pages/p17-*, p26-*, p27-*, p30-*
  app/sitemap.ts                          # 후반 계약 확정 후
```

- `page.tsx`/`layout.tsx`는 Server Component다. 페이지는 metadata·세션·prefetch·프레임을 담당하며 작은 상호작용 경계만 클라이언트로 둔다.
- 페이지 전용 코드는 `_components/_hooks/_lib`에 둔다. 실제 두 곳 이상에서 공유될 때 가장 가까운 상위 폴더로 옮긴다. 도메인 UI를 `components/ui`에 넣지 않는다.
- API 호출은 orval 또는 기존 `apiFetch`를 통한다. 페이지가 `mocks`, mock 플래그/쿠키를 import하지 않으며 직접 GitHub API를 호출하지 않는다.
- 서버 데이터는 TanStack Query, 단계/탭/필터/시트는 nuqs, 나머지 UI 상태만 Zustand를 사용한다. 계정·팀·방·필터가 필요한 쿼리 키에 포함돼야 한다.
- 정책 수치는 `policy.ts`를 차용한다. 현재 없는 팀 완료 취소·확정 기한, 소속 기간, 운영 idle 등 필요한 값도 구현 단계에서 해당 정책 근거와 함께 중앙화하며 화면·목업에 각각 흩어 쓰지 않는다. 날짜와 기간 경계는 기존 KST formatter를 사용한다.
- 시트는 `useOverlay` + 기존 Radix 컴포넌트만 사용한다. 팀 전환·PR·운영 상세/조치 등의 키 추가는 기존 `overlay-keys.ts`와의 통합 지점으로 관리한다. 닫기에서 push하지 않고 시트 간 전환은 replace한다.
- 팀/초대 변이 뒤에는 팀 목록·설정·멤버·관련 채팅 목록을, 운영 조치 뒤에는 회원 상세/목록·감사 로그를 무효화한다. 민감한 캐시는 계정 전환 때 제거한다.
- 팀·통계·운영·초대는 `noindex`다. 운영은 `nofollow`도 적용한다. 로그인 전용 화면의 metadata에는 팀명·이슈명·민감한 내용을 넣지 않는다.

### 미리보기와 후속 연동의 경계

- 설치 콜백의 `installation_id/state`를 프론트가 신뢰하거나 검증 성공으로 바꾸지 않는다. 기본 화면은 미확인이며 결과 선택은 **상태 화면 미리보기**로 명시한다. 실제 설치·중복 조직·권한 판정은 서버 검증 후 연결한다.
- 새 팀은 아직 없으므로 레포/보드 UI는 사용자가 명시적으로 선택한 **기존 오너 팀의 조회 데이터**로 확인한다. 기존 팀은 수정하지 않는다. 완료 미리보기의 이동도 선택한 기존 팀을 이용하며 새 팀이 생성됐다고 처리하지 않는다.
- 초대의 가입/한도 상태, 청구·소유권·완료 가능 여부, 운영 허용 액션은 조회용 잠정 DTO다. 프론트가 가입 기간·운영자 이름·쿼리 파라미터로 권한을 만들어 내지 않는다. OpenAPI 확정 시 생성 DTO로 전환한다.
- 대표 작업물 선택 UI는 현재 B 통계에 배치했다. A의 공통 선택 시트가 통합되면 해당 시트를 차용하고 저장 API를 연결한다. 현재는 기존 고정 상태 조회·선택·한도 안내만 제공한다.
- 이번 변경의 새 API 호출은 조회뿐이다. 설치/생성/수락/제재/해제/열람/환불/프로필 저장 변이는 추가하지 않았다. 공유·복사는 사용자가 버튼을 누른 경우에만 기존 링크를 전달한다.
- C의 내 이슈, A의 인증·온보딩·운영 OTP, D의 채팅/결제 동작, 실제 GitHub·Expo·sitemap 데이터 발행은 담당 경계/후속 통합으로 유지한다.

### 확인한 요청과 반영 방법

- C의 [PR #35 요청 댓글](https://github.com/likelion-backendschool-9th/Linker/pull/35#issuecomment-6556360529)은 B의 “내 이슈 전체 보기”를 `/workspace/issues`로 연결하는 요청이다. 조회 시 PR은 2026-11-01에 병합된 상태였고 원본 커밋은 `900b72a230ba6bc3f48d4ae00ab20cb301296e7c`였다.
